# Docker Caching

Tong's per-action content-addressed cache already prevents recompiles
across builds, but a naive `COPY . .` + `RUN tong build` Dockerfile
gets no layer caching: every source edit invalidates the layer holding
the store, so dependency results are lost and re-serialized on the next
build. Two commands make `docker build` layer-cache-friendly:

- `tong build --deps-only` — compile and cache only dependency actions.
- `tong dockerfile` — generate the exact `Dockerfile` + `.dockerignore`.

The invariant to preserve:

> Dep layers bust **iff** the lockfile content or the toolchain
> fingerprint changes; source edits touch only the app layer.

## The problem with naive images

1. `COPY . .` changes with every source edit → the layer containing it
   invalidates on every build.
2. The `.tong/` store (dependency compile results included) lives in the
   same layer → invalidation loses dep results → full dependency
   recompile.
3. Even when results survive, the layer diff containing the dep CAS is
   re-serialized on every push.

The fix is the same split `cargo-chef` gives Cargo users: rarely
changing inputs (manifests, lockfile, toolchain) in early layers, the
store flowing forward between stages, sources last.

## `tong build --deps-only`

Plans the full graph — feature unification and toolchain capture
unchanged — but executes only actions owned by **non-workspace**
packages:

- **Local** = workspace members. **Dep** = everything else (registry
  packages, external path dependencies).
- Dep actions run, execute, and are recorded in the action cache and
  the build-state manifest; local actions are skipped entirely (no
  lookup, no execution, no recording) and nothing is assembled.
- In native `Tong.toml` mode every target is local, so `--deps-only`
  executes nothing beyond toolchain capture; it becomes meaningful
  when network/fetch rules land.
- The deps stage runs with **only manifests + lockfile present, no
  local sources**: the `tong dockerfile` generator stages each member
  manifest at its real relative path, so planning's source-tree capture
  succeeds on the manifest-only tree (the captured tree is never
  executed in this mode, so its content is irrelevant).

The app stage then runs plain `tong build`: dep actions are cache hits
(input roots unchanged), local actions execute and materialize under
`.tong/out/<profile>/`.

## `tong dockerfile`

```sh
tong dockerfile [--profile <name>] [--base <image>] [--runtime-base <image>] [--output <dir>]
```

- `--profile` (default `dev`) is baked into the generated commands.
- `--base` (required unless `[toolchain.rust]` version is pinned; else
  defaults to `rust:<version>`) is the toolchain-stage image.
- `--runtime-base` (default `debian:bookworm-slim`) is the runtime
  stage base.
- `--output` (default `.`) receives `Dockerfile` + `.dockerignore`.

The `.dockerignore` always excludes `.git/`, `.tong/`, `target/`,
`**/target/` — the local dev store must never be copied over the
image's store.

Generated shape (the only substitutions are member-manifest COPY lines,
binary names, and the version pin):

```dockerfile
# syntax=docker/dockerfile:1
# Generated by `tong dockerfile` — do not edit, regenerate.

# Stage 0: tong toolchain (busts only when the tong version pin changes).
FROM rust:1.97-bookworm AS toolchain
RUN cargo install tong --version 0.1.0 --locked

# Stage 1: fetch + build deps. Busts only when manifests, Tong.lock, or
# the toolchain change — never on source edits.
FROM toolchain AS deps
WORKDIR /app
COPY Tong.toml Tong.lock ./
COPY Cargo.toml Cargo.lock ./
COPY crates/core/Cargo.toml crates/core/Cargo.toml
COPY crates/app/Cargo.toml crates/app/Cargo.toml
RUN tong fetch
RUN tong build --deps-only --profile dev

# Stage 2: app. Busts on every source change; dep actions are cache hits.
FROM deps AS app
COPY . .
RUN tong build --profile dev

# Stage 3: runtime.
FROM debian:bookworm-slim AS runtime
COPY --from=app /app/.tong/out/dev/app/app /usr/local/bin/app
ENTRYPOINT ["/usr/local/bin/app"]
```

Details:

- `Tong.toml`, `Tong.lock`, and `RUN tong fetch` are emitted only when
  the corresponding files exist; native-mode projects get `COPY
  Tong.toml` only.
- One `COPY --from=app` line per workspace binary (dependency-crate
  binaries are not copied); artifacts live at
  `.tong/out/<profile>/<bin>/<bin>`.
- Path dependencies *inside* the build context are copied in full
  (their actions execute in the deps stage); path deps *outside* the
  context are reported with a warning and must be copied in or
  vendored. Registry checkouts arrive via `tong fetch` from the store.
- `COPY . .` in stage 2 never overwrites the stage-1 store because
  `.dockerignore` keeps the local `.tong/` out of the context.

## The lock/fetch pattern

`tong lock` and `tong fetch` never read source files, so their `RUN`
layer busts exactly when a manifest or `Tong.lock` changes:

- A dependency declaration change → `Tong.lock` changes → fetch
  re-runs (a no-op for already-stored crates) and the deps layer
  rebuilds — correct, because deps actually changed.
- A src-only edit → manifests and `Tong.lock` unchanged → fetch and
  deps layers are cache hits.

**Commit `Tong.lock`** (like `Cargo.lock`) so docker never runs
`tong lock`; keep lock/fetch repo-side or in CI. `tong fetch --offline`
is **not** for docker builders — the builder needs network for the
first fetch.

## Store placement and GC in images

- **Default: keep the store in the image** (the deps layer). Zero
  config; docker's layer pointers dedupe the store content on push;
  recommended for CI.
- **Local iteration alternative:** BuildKit `--mount=type=cache` +
  `TONG_STORE_DIR=/tong-store` on a single-`RUN` pattern. Cache-mount
  contents are **not** in pushed layers, so this does not give the
  deps/app split — use the same cache id in every stage.
- **GC:** auto-GC after each build is fine as-is (the deps-only
  manifest merges the previous closure, so GC never deletes what the
  current workspace references). Optional
  `tong gc --older-than 0` in the final stage trims unmarked objects
  to shrink the image. Never `tong clean` inside an image — it wipes
  the store.
- **Toolchain capture:** the capture cache (`~/.cache/tong`) inside the
  image is written by the deps stage's cold capture; the app stage
  (`FROM deps`) pays only the stat-snapshot check. Don't exclude it
  from the toolchain/deps layers.

## GC safety of the two-stage flow

A deps-only build records only dependency actions and invalidates
nothing; its state manifest merges the previous manifest's object
closure, so the merged manifest stays the GC root and `tong gc
--older-than 0` after a deps-only build keeps dep results and local
trees. A later full build is a total cache hit — this exact scenario is
a regression test (`tong/tests/docker_stage.rs`).
